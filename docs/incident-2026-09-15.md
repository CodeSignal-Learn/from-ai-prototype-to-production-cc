# Incident: model provider outage, Tuesday 2026-09-15

A rehearsal on recorded traffic, run end to end with the alert rules, the runbook, and the
containment switch, and compared with the same outage left uncontained. Event log:
`results/events/week-2-incident.jsonl`, produced by

```text
python3 scripts/replay_traffic.py data/traffic/week-2.jsonl --events results/events/week-2-incident.jsonl \
    --flaky 96:114:rate_limit --failures 118:144:timeout --rules-from 122:150 --variant v1
```

which makes every other model call fail with a rate limit for requests 96 to 113 (the two
hours before; W2-0096's one call happened to succeed), times out every model call from the
arrival of request 118 (13:56) until the arrival of request 144 (Wednesday 08:26), whichever
request makes it (the outage: the rest of Tuesday), and processes requests 122 to 149 in rules
mode (the containment the on-call switched on). The comparison run,
`results/events/week-2-incident-uncontained.jsonl`, is the same command without
`--rules-from`: the same outage on the same week, left alone.

The replay records the events. The on-call's actions, the provider's status page, and the live
check before switching back are the runbook's steps played as a tabletop exercise: they are
assumed, and the log records only their effect (rules mode from W2-0122, the model again from
W2-0150).

No customer received anything: a rehearsal sends nothing, and in production nothing this

four requests with no draft because the model was

and an escalation share of 0.42 for the day against 0.31 for the same requests on the model.
Left uncontained, the same outage leaves 26 requests with no draft because the model was
unavailable, each after a 61.5 s wait.

## What the evidence showed at each step

- **The warning was the useful alert.** The rate limits produced no failed request, so nothing
  in the objectives moved; the retry share did. With the fallback staged at 13:00, the switch at
  14:45 was a decision already made. In the uncontained run, where nobody switched, the same
  outage hit 26 requests (W2-0118 to W2-0143, every request until the end of Tuesday).
- **Traces said what kind of failure to look for.** Three attempts, `LLMTimeout`, 61.5 s: the
  shape of a provider outage, or of our network to it, which the status page (degraded in this
  rehearsal) and the unchanged versions narrowed to the provider. Three `LLMRateLimited` would
  have pointed at load or the provider's quota; a plain `LLMError` at a broken deployment (key,
  model id), which no fallback repairs.
- **Versions ruled out the system.** Every request event before, during, and after carries
  prompt `81ec9d26f2c2`, variant `v1`, app `2.1.0`; the 28 handled in rules mode also carry
  `mode: rules`, which is the containment, not a deployment. Nothing was deployed, so the cause
  lay outside our release: in this rehearsal, the injected provider timeouts.
- **The evaluation had nothing to add**, and that is a finding: an outage is an operational
  event, and the scheduled evaluation run that week reported zero regressions against the
  reference runs: the shipped code and prompts were unchanged. It replays recorded answers, so it
  says nothing about the live model during the outage; availability is what moved.
- **Recovery was checked before and after the switch.** Before it: the provider's status and
  the live check of runbook B.3, both assumed in this tabletop. After it: the next windows'
  events, which the log records (unavailable rate 0, `versions.mode` back to `model`).

## Follow-ups

1. Rules mode escalates more requests than model mode (15 of the 28 contained requests, against
   10 of the same 28 on the model). The support lead accepted that for an afternoon; a longer
   outage needs a staffing note in the runbook.
2. `ASSISTANT_MAX_RETRIES=0` during a confirmed outage would have turned 61.5 s waits into
   20 s waits for the three requests hit between the alert and the switch. Set before the outage
   is confirmed, it costs more than it saves: replayed with it set all day, the flaky hours' rate
   limits also become unavailable steps (19 requests unavailable instead of 4). Added to the
   runbook's switches.
3. The retry warning's threshold, 0.2 over two hours, fired an hour before the outage here. On a
   provider that degrades faster it fires at the same time as the outage alert; the point stands
   either way, since its response is to stage the fallback.

## What this rehearsal cannot show

Simulated latency and injected failures on the replay client. The live provider's failure
shape, how long its outages last, and whether its status page leads or lags the failures are
unknown until the service runs on real traffic. The alert thresholds are set against the live
median latency and timeout; they are not tuned against a live outage.
