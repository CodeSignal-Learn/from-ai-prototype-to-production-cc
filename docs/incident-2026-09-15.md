# Incident: model provider outage, Tuesday 2026-09-15

A rehearsal on recorded traffic, run end to end with the alert rules, the runbook, and the
containment switch, and compared with the same outage left uncontained. Event log:
`results/events/week-2-incident.jsonl`, produced by

```text
python3 scripts/replay_traffic.py data/traffic/week-2.jsonl --events results/events/week-2-incident.jsonl \
    --flaky 96:114:rate_limit --failures 118:12:timeout --rules-from 122:150
```

which makes every other model call fail with a rate limit for requests 96 to 113 (the hour
before), fails twelve calls with timeouts from request 118 (the outage), and processes requests
122 to 149 in rules mode (the containment the on-call switched on). The comparison run,
`results/events/week-1-incidents.jsonl`, has an outage of thirty timeouts and no containment.

## Impact

| | This incident (contained) | Same outage, uncontained (`week-1-incidents`) |
| --- | --- | --- |
| Requests that reached a person with no draft because the model was unavailable | 4 | 10 |
| Requests handled on template drafts | 28 | 0 |
| Availability for the day | 0.944 | 0.861 |
| Latency p95 for the day | 6.0 s | 61.5 s |
| Customers affected | 0 | 0 |

No customer received anything: nothing this assistant produces is sent without a person.
The cost of the outage is agent time: four requests with no draft at all, twenty-eight with a
template draft instead of a model draft, and an afternoon where the escalation share ran at
0.42 instead of about 0.28.

## What the evidence showed at each step

- **The warning was the useful alert.** The rate limits produced no failed request, so nothing
  in the objectives moved; the retry share did. With the fallback staged at 13:00, the switch at
  14:45 was a decision already made. In the uncontained run the same outage hit ten requests
  because the second-window rule was followed to the letter.
- **Traces said what kind of failure it was.** Three attempts, `LLMTimeout`, 61.5 s: a provider
  outage. Three `LLMRateLimited` would have meant lowering concurrency was the fix; a plain
  `LLMError` would have meant a broken deployment (key, model id), which no fallback repairs.
- **Versions ruled out the system.** Every request event before, during, and after carries
  prompt `81ec9d26f2c2`, variant `v1`, app `2.1.0`. Nothing was deployed; the provider changed.
- **The evaluation had nothing to add**, and that is a finding: an outage is an operational
  event, and the scheduled evaluation run that week reported zero regressions against the
  reference runs. Quality did not move; availability did.
- **Recovery was verified, not assumed.** Two things were checked before switching back: the
  provider's own status, and the next windows' events after the switch (unavailable rate 0,
  `versions.mode` back to `model`).

## Follow-ups

1. Rules mode escalates more requests than model mode (0.42 against 0.28 for the day). The
   support lead accepted that for an afternoon; a longer outage needs a staffing note in the
   runbook.
2. `ASSISTANT_MAX_RETRIES=0` during a confirmed outage would have turned 61.5 s waits into
   20 s waits for the three requests hit between the alert and the switch. Added to the
   runbook's switches.
3. The retry warning's threshold, 0.2 over two hours, fired an hour before the outage here. On a
   provider that degrades faster it fires at the same time as the outage alert; the point stands
   either way, since its response is to stage the fallback.

## What this rehearsal cannot show

Simulated latency and injected failures on the replay client. The live provider's failure
shape, how long its outages last, and whether its status page leads or lags the failures are
unknown until the service runs on real traffic. The alert thresholds are set against the live
median latency and timeout; they are not tuned against a live outage.
